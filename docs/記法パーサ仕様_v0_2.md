## 0. この文書の位置づけ

要件定義書v0.5の **6.3 記法** を実装可能な粒度まで展開したもの。ADR-001により表面はパーサの出力から生成されるため、**パーサが壊れると全カードが読めなくなる**。したがって仕様を先に固定し、テストを先に書く。

本文書で「決定」としたものは、要件定義書v0.6へ反映する（→ §9）。

## 1. 設計原則

以降の全ての判断はこの3つから導く。

| ID | 原則 | 理由 |
|---|---|---|
| P-1 | **非破壊**：どんな入力でもパーサは例外を投げず、テキストを1文字も失わない | 課題B（入力内容が失われる）が本プロダクトの出発点。記法エラーでの保存拒否は、その課題を自分で再現することになる |
| P-2 | **純粋関数**：`parse()` はDB・React・Next.jsを一切知らない。入力は `string`、出力は配列 | ADR-007。サーバーを起動せずに単体テストできる状態を保つ |
| P-3 | **安全側**：同一性が疑わしい穴は、統計を継承させない | ミス回数が誤って引き継がれると、F-10の「弱点の指標」という役割そのものが壊れる。リセットは回復可能だが、汚染は検知できない |

> P-1の帰結として、**「不正な記法」という状態は存在しない**。閉じられていない `〈` は単なる文字として扱われる。バリデーションエラーを返す設計にはしない。

## 2. 字句仕様

### 2.1 使用する文字と正規化

伏せ字の区切りには **U+3008 / U+3009**（`〈` `〉` LEFT/RIGHT ANGLE BRACKET）を正とする。

問題は、見た目がほぼ同じ文字が複数存在すること。IMEや貼り付け元によって別のコードポイントが混入する。

| 文字 | コードポイント | NFC正規化の結果 | 対応 |
|---|---|---|---|
| `〈` | U+3008 | U+3008 | **正** |
| `〈` | U+2329 | **U+3008** | NFCで自動的に吸収される |
| `⟨` | U+27E8 | U+27E8（**変化しない**） | **明示的な置換が必要** |
| `《` | U+300A | U+300A | 別記法として**予約のみ**（v1では実装しない。§2.7） |

**決定**：保存前に以下の順で正規化する。

1. `String.prototype.normalize("NFC")` を適用（U+2329 → U+3008 を吸収）
2. U+27E8 → U+3008、U+27E9 → U+3009 に置換
3. 改行コードを `\n` に統一（CRLF → LF）

> NFKCは使わない。全角英数字（`Ａ` → `A`）まで潰してしまい、板書の表記を勝手に書き換えることになるため。
> 正規化は**保存時に本文へ破壊的に適用する**。パース時に毎回かけると、DB上の本文と表示が乖離して原因調査が困難になる。

### 2.2 エスケープ

`〈 〉` は数学・物理で期待値や内積の表記として実際に使われる（`〈x〉`, `〈ψ|φ〉`）。大学理系科目の板書を対象とする以上、リテラルとして書く手段は必須。

**決定**：バックスラッシュによるエスケープを採用する。

| 入力 | 出力 |
|---|---|
| `\〈` | リテラルの `〈` |
| `\〉` | リテラルの `〉` |
| `\《` `\》` | リテラルの `《` `》` |
| `\\` | リテラルの `\` |
| **上記以外の `\x`** | **`\x` をそのまま出力**（バックスラッシュを消さない） |
| 末尾の `\` | リテラルの `\` |

最後の2行が重要。`\frac` や `\alpha` のバックスラッシュを黙って削除しない、という規則になっている。これによりv3のLaTeX対応時に、既存カードの本文を一括変換する必要がなくなる。

> エスケープは後付けが極めて高くつく。導入後に規則を変えると、既に保存された全カードの解釈が変わるため。v1で入れる。

### 2.3 出力の型

```typescript
export type Token = TextToken | BlankToken;

export type TextToken = {
  kind: "text";
  raw: string;    // 原文の該当区間（エスケープ('\')解除前） 例:\<x>
  value: string;  // 表示用（エスケープ解除後）例:<x>
};

export type BlankToken = {
  kind: "blank";
  raw: string;     // 原文の該当区間。'〈' と '〉' を含む
  answer: string;  // 表示用。区切り文字を除き、前後の空白をトリムし、エスケープ解除済み
  index: number;   // 本文中で何番目の穴か（0始まり）
};

export function parse(body: string): Token[];
```

`raw` と `value` / `answer` を分けているのは P-1 のため。**全トークンの `raw` を連結すると原文に完全一致する**（§7.1 の不変条件I-1）。この性質があるので、パーサが何をどう解釈しても原文は復元でき、本文を失う経路が存在しなくなる。

### 2.4 状態機械

正規表現は使わない。エスケープ規則が絡むと `/〈([^〉]*)〉/g` のような素朴なパターンでは正しく処理できず、無理に書くと可読性とテスト容易性を同時に失う。単一パスの状態機械で書く。

状態は `OUTSIDE` / `INSIDE` の2つ。`open` は `〈` を読んだ位置を保持する。

| (現)状態 | 入力 | 動作 | 次状態 |
|---|---|---|---|
| OUTSIDE | `\` + 記法文字 | 2文字消費し、2文字目をテキストに追加 | OUTSIDE |
| OUTSIDE | `\` + その他 | `\` をテキストに追加（1文字消費） | OUTSIDE |
| OUTSIDE | `〈` | ここまでのテキストを確定。`open` を記録 | INSIDE |
| OUTSIDE | `〉` | テキストに追加（対応する開きがないため） | OUTSIDE |
| OUTSIDE | その他 | テキストに追加 | OUTSIDE |
| OUTSIDE | EOF | テキストを確定 | 終了 |
| INSIDE | `\` + 記法文字 | 2文字消費し、2文字目を内容に追加 | INSIDE |
| INSIDE | `\` + その他 | `\` を内容に追加 | INSIDE |
| INSIDE | `〉`（内容が非空） | **Blankトークンを確定** | OUTSIDE |
| INSIDE | `〉`（内容が空） | `〈〉` をテキストに追加 | OUTSIDE |
| INSIDE | `〈` | `open` から直前までをテキストに追加し、`open` を現在位置に移す | INSIDE |
| INSIDE | `\n` | `open` から `\n` までをテキストに追加 | OUTSIDE |
| INSIDE | その他 | 内容に追加 | INSIDE |
| INSIDE | EOF | `open` から末尾までをテキストに追加 | 終了 |

計算量は O(n)。巻き戻しは発生しない。

### 2.5 異常系と、その解釈

上表から導かれる具体例。**全て「エラー」ではなく「そう解釈される」**。

| 入力 | 結果 | 意図 |
|---|---|---|
| `〈微分〉` | blank(`微分`) | 基本形 |
| `〈 微分 〉` | blank(`微分`) | 内側の前後空白はトリム。`raw` は原文のまま |
| `〈〉` | text(`〈〉`) | 空の穴は答えが存在しないので穴にしない |
| `A〉B` | text(`A〉B`) | 孤立した閉じは文字 |
| `〈A` | text(`〈A`) | 閉じられない開きは文字 |
| `〈A\nB〉` | text(`〈A\nB〉`) | 穴は改行をまたげない（§2.6） |
| `〈A〈B〉` | text(`〈A`) + blank(`B`) | 内側が勝つ。入れ子は作らない |
| `〈A〉〈B〉` | blank(`A`) + blank(`B`) | 連続は可 |
| `\〈x\〉` | text(`〈x〉`) | 期待値記号のリテラル |
| `\frac{1}{2}` | text(`\frac{1}{2}`) | LaTeX前方互換 |

### 2.6 なぜ穴は改行をまたげないか

- 表面では穴を固定幅のプレースホルダに置換する（§4）。複数行を1つのプレースホルダに畳むと、行数が変わって板書のレイアウトが崩れる
- `〈` の閉じ忘れが1個あるだけで、以降の本文全体が1個の巨大な穴として解釈される事故を防げる。改行で必ず切れるため、被害が1行に限定される

### 2.7 `《 》` の扱い（v1では実装しない）

Q-07により、裏面のみ表示の記法はv2へ送る。v1での扱いは以下の通り。

- **`《 》` は通常の文字として扱う。**状態機械に分岐を追加しない
- ただし**エスケープ対象としては予約する**（`\《` → `《`）。エスケープ規則の後付けは既存カードの解釈を変えるため（ADR-011）
- **保存時に、本文中の生の `《` または `》` を検出したら記録する**（警告は出さない）

最後の項目の理由：v2で `《 》` を記法として実装すると、**v1時代に書かれた生の `《 》` を含むカードは解釈が変わる**。これは後方互換性を壊す唯一の既知の経路である。実際に使われているカードが存在するかを事前に把握できれば、v2の移行方針（一括エスケープするか、放置するか）を実データに基づいて決められる。検出だけしておけばコストはほぼゼロで済む。

## 3. 同一性解決（保存時）

**本仕様の中心。パーサ本体よりこちらの方が難しい。**

### 3.1 なぜ必要か

ADR-002は「穴の生成時に不変IDを付与し、統計はIDに紐づける」と決めた。しかし6.3で「不変IDはユーザーの入力には現れない」とも決めている。つまり**本文テキストのどこにもIDが書かれていない**。

すると保存時、アプリの手元にあるのは以下の2つだけになる。

- 旧: DBにある Blank レコード群（IDと統計を持つ）
- 新: 今回パースした BlankToken の列（IDを持たない）

この2つを**突き合わせて対応付ける処理**がなければ、IDは不変になりようがない。受け入れ条件「カード本文を編集して文字数が変わっても、各穴のミス回数が保持されている」は、この処理の品質そのものを問うている。

> **代替案：本文にIDを埋め込む**（`〈#k3f9|微分〉` 等）
> 突き合わせが不要になり確実だが、(a) 編集画面にIDが露出する（隠すなら本文の二重管理が発生し、ADR-001の趣旨に反する）、(b) ユーザーがIDを壊せる、(c) 文字数制限をIDが圧迫する（課題D）。**不採用**（ADR-009）。

### 3.2 データモデルへの追加

要件定義書 6.1 の Blank に、以下を追加する。

| フィールド | 型 | 用途 |
|---|---|---|
| `ordinal` | `Int?` | 本文中で何番目の穴か（0始まり）。**保存のたびに更新される可変値**。削除済みは `null` |
| `answerKey` | `String` | 照合用に正規化した答え。可変 |
| `deletedAt` | `DateTime?` | 本文から消えた穴の目印。レコードもBlankLogも削除しない |

```prisma
model Blank {
  id           String    @id @default(cuid())
  cardId       String
  card         Card      @relation(fields: [cardId], references: [id], onDelete: Cascade)
  ordinal      Int?
  answerKey    String
  resetAt      DateTime  @default(now())
  maxMissCount Int       @default(0)
  deletedAt    DateTime?
  logs         BlankLog[]

  @@unique([cardId, ordinal])
  @@index([cardId, answerKey])
}
```

補足：

- **答えの本文は保存しない。** `answerKey` は照合専用の正規化文字列であり、表示用の答えは常に本文をパースして得る。答えを二重に持つとADR-001と同じ不整合が起きる
- `@@unique([cardId, ordinal])` は PostgreSQL では NULL 同士が衝突しないため、削除済みBlankが複数あっても問題ない
- `ordinal` を持つことで、**表示時にはマッチングを走らせない**。n番目のBlankTokenは `ordinal = n` のレコードを引くだけで済む。マッチングは保存時だけの処理になる

`answerKey` の正規化規則：NFC → 前後トリム → 連続する空白を1つに畳む。大文字小文字は畳まない（`dx` と `DX` は別物）。

### 3.3 マッチングアルゴリズム

入力：`oldBlanks`（当該カードの全Blank。削除済みを含む）、`newTokens`（BlankToken列）

**Pass 1：`ordinal` と `answerKey` が両方一致**
未編集の穴、および穴の外側だけを加筆した場合をここで拾う。想定される編集の大半はここで終わる。

**Pass 2：`answerKey` が一致し、`ordinal` が最も近いもの**
穴を途中に挿入・削除して以降の `ordinal` が全てずれた場合を拾う。同じ答えが複数ある場合（`〈微分〉` が3箇所等）も、距離で一意に決まる。距離が同点なら `ordinal` の小さい方を採る（決定性のため）。

**Pass 3：残り**
- 余った新トークン → 新規Blankを作成（新ID、`resetAt = now`、`maxMissCount = 0`）
- 余った旧Blank → `ordinal = null`, `deletedAt = now` にする。**レコードもBlankLogも削除しない**（5.3）

いずれのPassでも、マッチした旧Blankは `ordinal` と `answerKey` を新しい値で更新する。

> Pass 1・2 とも、削除済みBlank（`deletedAt != null`）も候補に含める。ただし優先度は生存Blankより下げる。誤って消した穴を貼り直したときに統計が戻るため。課題Bの文脈では、この復活は実装コストに見合う。マッチした時点で `deletedAt = null` に戻す。

### 3.4 意図的に採用しない規則

**「`ordinal` が一致すれば `answerKey` が違ってもマッチさせる」は v1 では採用しない。**

採用すれば、穴の中の誤字を直したときに統計が保たれる（利点）。一方で `〈微分〉` を `〈積分〉` に差し替えたときも同一とみなされ、**別概念のミス回数を継承する**。

原則P-3に従い、不採用とする。ADR-005（「1つでもミスでagain」）と同じく、安全側に倒す判断。

**この結果生じる制約**（要件定義書 §9 に転記）：

> 穴の**中身**を編集すると、その穴は新規の穴として扱われ、ミス回数がリセットされる。BlankLogは保持されるため統計自体は失われないが、v1では閲覧・再紐付けの手段がない。

v2で「この穴は編集前と同じ扱いにする」を明示的に選ぶUIを検討する。推測ではなくユーザーの宣言で解決すべき問題であるため。

## 4. 表面の生成

```typescript
// 純粋関数。Reactを知らない。
export function toFront(tokens: Token[]): Token[];
```

- テキストトークンはそのまま
- 穴は固定幅のプレースホルダに置換する。**答えの文字数を反映させない**（長さは強いヒントになる。ヒント機能は3.2で対象外）
- ミス回数バッジをプレースホルダの直近に置く（F-10）。表示規則は要件定義書 §4補足の表に従う

React側の要求：

- 描画は `dangerouslySetInnerHTML` を**使わない**。トークン配列をそのままReact要素へ写像する。パーサ出力はデータであってHTMLではない
- 穴要素の `key` は `blankId` を使う。配列インデックスを使うと、加筆で穴がずれたときに開閉状態が別の穴へ引き継がれる
- 「どの穴を開いたか」はコンポーネントのstate（`Set<blankId>`）。カード単位ではなく穴単位で持つ（F-02／課題C）

## 5. 文字数カウント

要件定義書6.5・ADR-012で確定した規則の実装仕様。

### 5.1 対象と重み

対象は `toBack()` の出力、すなわち区切り文字とエスケープ用バックスラッシュを除いた表示テキスト。`〈金属〉` は2字。

| 対象 | 半角単位 | 表示上 |
|---|---|---|
| ASCII表示可能文字（U+0020〜U+007E） | 1 | 0.5字 |
| 改行 `\n` | 2 | 1字 |
| 上記以外（日本語・ギリシャ文字・絵文字など） | 2 | 1字 |

内部は整数の**半角単位**（半角=1／全角=2）で保持する。上限500字＝**1000半角単位**。0.5は二進で正確に表現できるため浮動小数点誤差は生じないが、整数で持つ方がテストの表明が単純になる。

### 5.2 数える単位

`String.prototype.length` はUTF-16コードユニット数であり、使えない。Node 22で実測した値：

| 文字列 | コードユニット | コードポイント | 書記素 |
|---|---|---|---|
| `𝕏` | 2 | 1 | 1 |
| `👨‍👩‍👧` | 8 | 5 | 1 |
| `ﾊﾝｶｸ` | 4 | 4 | 4 |

見た目1文字の絵文字が8字を消費するのは、ユーザーから見て説明のつかない挙動になる。**書記素クラスタ**で数える。`Intl.Segmenter` はNode 18以降および現行の全ブラウザで利用でき、依存パッケージを増やさずに済む。

### 5.3 実装

```typescript
const ASCII_PRINTABLE = /^[\u0020-\u007E]$/;
const LIMIT_HALF_UNITS = 1000; // 500字

const segmenter = new Intl.Segmenter("ja", { granularity: "grapheme" });

/** 半角単位で数える。半角=1, 全角=2 */
export function countHalfUnits(back: string): number {
  let units = 0;
  for (const { segment } of segmenter.segment(back)) {
    units += ASCII_PRINTABLE.test(segment) ? 1 : 2;
  }
  return units;
}

export function toDisplayLength(units: number): number {
  return units / 2;
}

export function isOverLimit(units: number): boolean {
  return units > LIMIT_HALF_UNITS;
}
```

`ASCII_PRINTABLE` は1文字にしかマッチしないため、複数コードポイントからなる書記素（絵文字のZWJ連結、異体字セレクタ付き文字など）は自動的に2単位に落ちる。改行 `\n` もASCII表示可能文字の範囲外（U+000A）であるため2単位となり、「改行は1字」の規則が追加の分岐なしで満たされる。

> `segmenter` はモジュールスコープで1つだけ生成する。`Intl.Segmenter` の生成はキー入力ごとに呼ぶには重い。

### 5.4 上限超過時

**保存はブロックしない**（原則P-1／ADR-010）。文字数を理由に保存を拒否すると、超過した状態の編集内容が失われる経路ができる。

超過時はカウンタの視認性を**上げる**（課題F：「文字数制限を超えると文字数カウントが視認しづらくなる」）。

---

## 6. 上限値

| 項目 | 値 | 理由 |
|---|---|---|
| 1カードあたりの穴の数 | 200 | 受け入れ条件は20箇所以上。桁1つの余裕を持たせつつ、病的な入力（`〈a〉` × 10000）でのマッチング計算量を抑える |
| 本文の長さ | **500字（1000半角単位）** | ReminDOを踏襲（ADR-003・ADR-012）。超過しても保存はブロックしない |

穴が上限を超えた場合も保存はブロックせず、201個目以降は穴にせずテキストとして扱い、警告を出す（P-1）。

## 7. テスト方針

ADR-001の「テストを厚くする」に対応する具体策。ランナーは Vitest（TypeScriptをそのまま実行でき、設定がほぼ不要）。

### 7.1 不変条件（プロパティテスト）

`fast-check` でランダム文字列を生成し、以下が**常に**成り立つことを検証する。ケースを人力で列挙するより、想定外の入力を効率よく見つけられる。

| ID | 不変条件 |
|---|---|
| I-1 | 全トークンの `raw` を連結すると入力文字列に完全一致する（**最重要**。§2.3） |
| I-2 | `parse()` はどんな入力でも例外を投げない（P-1） |
| I-3 | `index` は 0 から連番で、`kind === "blank"` のトークンにのみ付く |
| I-4 | `toFront()` の出力に、いずれの `answer` の文字列も含まれない |
| I-5 | 同じ入力からは常に同じ出力が得られる（決定性） |

### 7.2 ケーステスト

- §2.5 の表を、そのままテーブル駆動テストにする
- マッチングは「編集前の本文 → 編集後の本文 → 期待されるID対応」の三つ組で書く。最低限、以下を含める：
  - 変更なし
  - 穴の外側に加筆（受け入れ条件そのもの）
  - 先頭に穴を挿入（全 `ordinal` がずれる）
  - 中間の穴を削除
  - 同一の答えが3箇所ある状態で中央を削除
  - 穴を削除して同じ内容を貼り直す（復活）
  - 穴の中身を編集（**新規扱いになることを固定する**。§3.4）

### 7.3 文字数カウントのテスト

`String.length` への退行を防ぐため、以下を固定する。

| 入力 | 期待（半角単位） | 意図 |
|---|---|---|
| `abc` | 3 | ASCII＝各1 |
| `あいう` | 6 | 全角＝各2 |
| `a\nb` | 4 | 改行は2（＝1字） |
| `𝕏` | 2 | コードユニット数(2)と一致するが、書記素1個としての2であること |
| `👨‍👩‍👧` | 2 | **`.length` なら8。ここが退行しやすい** |
| `ﾊﾝｶｸ` | 8 | 半角カナはASCII外。抜け道にしない |
| `αβ` | 4 | ギリシャ文字は全角扱い（ADR-012） |
| `〈金属〉` の本文 | 4 | 区切り文字を数えない（§5.1） |
| `\〈x\〉` の本文 | 5 | エスケープのバックスラッシュを数えない。`〈`=2, `x`=1, `〉`=2 |

> この表の全件は §5.3 の実装で実測検証済み（Node 22）。
