## 1. 背景と課題

### 1.1 現状

暗記カード（最大500文字）を忘却曲線に沿ったスケジュールで通知する反復記憶アプリ「ReminDO」を約7年間使用してきた。

主な使い方は以下の通り。

1. 授業の板書を、内容が関連している500字以下のメモ × n個に分解する
2. 自力で想起したい内容を虫食いに設定（「○○」で置換）したメモを表面に登録する
3. メモの元文を裏面に登録する
4. 忘却曲線に厳密に従わなくてもよいので、毎日決まった時間に作成したカードへ回答する

この使い方を続ける中で多くの不満点が浮き彫りになり、かつ2026年現在に至っても自分の使い方に最適なアプリを見つけられなかったため、自作を決意した。

### 1.2 課題

既存の反復学習ツールは1問1答形式を前提としており、構造を持ったノート（板書）を扱えない。無理に扱おうとすると不便が目立つ。

なお、以下の課題群に明確な優先順位はなく、並列に存在している。

#### 課題A：カード間の連続性が失われる

長い板書を複数カードに分解すると、①→②→③という論理の流れが切れる。カード同士を辿る手段がないため、分割した瞬間に文脈が失われる。

- 「次へ」で連続するカードへ遷移する機能がない
- 1問1答カードを想定した設計のため、板書を書き込むと復習計画が破綻する

> 補足：**カード間を辿れるならば、1枚500字という制限は許容できる。** 文字数制限自体は要約を強制するため、学習上はむしろ望ましいと考えている。

#### 課題B：入力内容が失われる

- 自動保存がないため、保存前に油断してブラウザで情報収集していると、勝手にページが再読み込みされてデータが消える
- 入力画像が一定時間経過で消える
- 数年ぶりのログインでカードが全消失した（浪人時代の資産）

#### 課題C：想起の粒度を制御できない

- 「裏面を見る」をタップすると、そのカードの虫食いが**すべて**開いてしまう。画面の一部を手で隠しながら使う必要がある

#### 課題D：文字数枠を本文以外が圧迫する

- 参考書本文の引用（定義や解説など、これ以上要約しづらいもの）で文字数を消費する
- ソースURL枠が1つしかなく、本文枠を使わざるを得ない
- 数字・アルファベットの消費が大きい
- 改行ごとに2文字消費される

#### 課題E：一覧・回遊性が乏しい

- カード一覧にソート機能がない
- フリックでしか全カードを閲覧できない
- 読み込み後、最初のタップで一番上に戻される
- 画像を等倍で見るたびに新規タブが開かれる

#### 課題F：表現力の制約

- LaTeXに対応していない
- 絵文字を使うと不具合が発生する
- 表裏で画像を1つずつしか添付できない
- タグが3つまでしか同時使用できない
- カードのタイトル欄が独立していない
- Chrome拡張からのカード登録が1文までしか対応していない
- 文字数制限を超えると文字数カウントが視認しづらくなる

### 1.3 このプロダクトが解決すること

構造を持ったノート形式を前提とし、上記の不満点を随時改善する。

## 3. スコープ

### 3.1 やること（v1）

- カードの作成・削除（カードNo.付与）
- **連続するカードへの遷移**（次へ／前へ）
- カードの自動保存（入力が途切れた一定秒後、および一定時間ごと）
- カード一覧の表示（デフォルトは表面）
- 忘却曲線に沿った復習スケジューリング（**カード単位**）
- 穴ごとの正誤・日時の記録（履歴は削除しない）、および**ミス回数の事前表示**
- 復習デッドライン超過時のミス回数リセット（最大値は保持）
- ネットに繋げればデバイス問わず利用可能

### 3.2 やらないこと（v1では対象外）

| 対象外 | 理由 | 将来 |
|---|---|---|
| 画像入力 | 実装コストが大きい | v2 |
| 複数ユーザーでの共同編集 | 想定ユーザーが単独利用のため | なし |
| 穴ごとの統計の**閲覧UI**（クリックで詳細表示） | 記録はv1で行うが、表示画面は独立した実装が必要 | v2 |
| 学習履歴の閲覧画面 | 同上 | v2 |
| カードのエクスポート機能 | 優先順位が落ちる | v2 |
| タグ付け機能 | 同上 | v2 |
| 忘却曲線以外のスケジュール設定 | 同上 | v2 |
| 今日消化すべきカード枚数の表示 | 同上 | v2 |
| カード検索・ソート | 同上 | v2 |
| 引用・ソースURLの別枠管理 | 同上（設計方針はADR-003に記載） | v2 |
| 自己正誤の細かいグラデーション | 同上 | v2 |
| 虫食いのヒント機能 | 同上 | v2 |
| バックアップ機能 | 同上 | v2 |
| LaTeX対応 | 記法パーサとの干渉検討が必要。コア安定後に着手 | v3以降 |
| カード作成のTips表示 | 現時点で自分以外のユーザーを想定していないため | 他ユーザーを想定する段階で必ず入れたい |

## 4. 機能要件

| ID | 要件 | 理由 | 優先度 |
|---|---|---|---|
| F-01 | 学習者として、文中の任意箇所を記法で伏せたい | 文脈を保ったまま想起したいから | 必須 |
| F-02 | 学習者として、伏せ字を個別にクリックして正解を表示したい | 想起の粒度を自分で制御したいから（課題C） | 必須 |
| F-03 | 学習者として、伏せ字ごとに正誤を自己申告したい | どこを落としたか記録したいから | 必須 |
| F-04 | 学習者として、カードが自動で復習日程に載ってほしい | 復習タイミングを自分で管理したくないから | 必須 |
| F-05 | 学習者として、編集内容がこまめに自動保存されてほしい | 保存忘れ・不具合・障害で失いたくないから（課題B） | 必須 |
| F-06 | 学習者として、PC・スマホどちらからも使いたい | 場所を選ばず復習したいから | 必須 |
| F-07 | 学習者として、カードを削除したい | 整理したいから | 必須 |
| F-08 | 学習者として、定着度に関係なく作成済みカードを全て閲覧したい | 時間が空いてからの復習で使いたいから | 必須 |
| F-09 | 学習者として、連続するカードへワンタップで移動したい | 分割した板書の流れを辿りたいから（課題A） | 必須 |
| F-10 | 学習者として、過去にミスした穴が答える前から判別できてほしい | 弱点に集中して復習効率を上げたいから | 必須 |
| F-11 | 学習者として、復習を放置した穴のミス回数はリセットされてほしい | 放置由来のミスが蓄積すると、ミス回数表示が弱点の指標として機能しなくなるから | 必須 |

### 補足

**F-04について**：カードが増えると必ず消化が追いつかなくなる。よってスケジュールはあくまで「おすすめ計画」という位置づけを保ち、消化枚数はユーザーに委ねる。無理なく実行可能で、かつ復習回数が少ないカードを優先することを考慮したうえで、忘却曲線にある程度従う形とする。

**F-05について**：入力が途切れた1秒後の保存と、入力開始からの定期保存を併用する。

**F-10について**：ミス回数は伏せ字を開く**前**から可視とする。答えの手がかりになる可能性はあるが、弱点に集中できる利得が上回ると判断した。表示は穴の直近に配置する。

表示ルールは以下の通り。

| 状態 | 表示例 | 意味 |
|---|---|---|
| 現在値＝最大値 | `3` | 復習計画を守ったうえで3回ミスした |
| 現在値≠最大値 | `¹₃` | 現在1回。過去に最大3回まで到達したことがある |

**F-11について**：復習デッドラインを超過した穴は、現在のミス回数をリセットする。ただし最大ミス回数は独立して保持し続けるため、過去に苦戦した事実は失われない。リセットは記録の削除ではなく集計起点の移動として実装する（ADR-004）。

## 5. 非機能要件

### 5.1 性能

| 項目 | 目標値 | 備考 |
|---|---|---|
| 想定カード総数 | 10,000枚 | 浪人1年で約5,000枚作成した実績に基づく |
| 1回の復習セッションの出題数 | 無制限 | いずれ消化が追いつかなくなるため上限を設けない |
| カード表示のレスポンス | 95%のリクエストで500ms以内 | 一定距離スクロールごとにn枚を追加表示する想定 |
| 同時利用者数 | 3 | 自分が操作するデバイス数 |

### 5.2 可用性

- **どれくらい落ちてよいか**：月間99%（＝1か月あたり約7.2時間までの停止を許容する。720時間 × 1%）
- **その水準にした理由**：復習は数時間遅れても学習効果は大きく損なわれない。一方で99.9%（月43分）を目指すとコストが跳ね上がり、個人開発の稼働時間に見合わない
- **落ちた場合の影響**：その日の復習ができない。学習の遅延は生じるが、データが失われなければ回復可能

### 5.3 データ保全

- **失ってはいけないデータ**：カード本文、作成日時、**穴ごとの正誤統計（BlankLog）**
- **統計を保全対象とする理由**：復習効率化の根拠データであり、再蓄積には実際に学習し直す時間が必要なため復元できない
- **バックアップ方針**：v1では自動バックアップ機能は未実装。ただしデータベース単体での復旧手段を確保しておく

### 5.4 セキュリティ

- **認証**：必要。3デバイス間で同期するためデータをサーバーに置くため、URLを知られた第三者による読み書きを防ぐ必要がある。v1では単一ユーザー向けの簡易なログインで十分とする
- **扱う個人情報**：認証情報（メールアドレス、パスワード）のみ。カード本文は学習内容であり個人情報を含めない運用とする
- **実装上の要求**：パスワードは平文で保存せず、ハッシュ化して保管する

### 5.5 運用

- **監視対象**：v1時点では未定（段階6で定義）
- **ログ方針**：v1時点では未定（段階6で定義）

## 6. データモデル

### 6.1 主要エンティティ

| エンティティ | 保持する情報 | 備考 |
|---|---|---|
| Card | カードNo.、本文（記法込み）、作成日時、更新日時 | 表面は保存せず記法の置換で生成する |
| Blank | **不変ID**、所属カード、集計起点日時(resetAt)、最大ミス回数 | 位置ではなくIDで同一性を保つ（ADR-002） |
| BlankLog | 所属Blank、回答日時、正誤 | 全履歴を保持し削除しない |
| Review | 所属カード、復習日、成績、次回日、間隔、EF | SM-2のパラメータ |

> EF（Ease Factor）＝カードごとの「憶えやすさ係数」。SM-2ではこの値によって復習間隔の伸び方が変わる。仕様調査の際に確認する。

**ミス回数の導出**

- 現在ミス回数 ＝ `resetAt` 以降の BlankLog のうち誤答の件数
- 最大ミス回数 ＝ Blank が保持する独立フィールド（リセットされない）
- デッドライン超過時は `resetAt` を更新するのみで、BlankLog は削除しない

### 6.2 スケジューリング

- **アルゴリズム**：SM-2（公開仕様を実装する。自作しない）
- **単位**：カード単位。穴単位のスケジューリングは行わない
- **成績の決め方**：カード内の穴を **1つでもミスすれば again** とする（最悪基準）。正解数に応じた段階評価はv1では実装しない
- **穴の扱い**：正誤と日時は記録する。スケジュールへの反映は上記の判定のみ

### 6.3 記法

- 伏せ字：`〈 〉` で囲む
- 裏面のみに表示する補足：表面で不可視にする記法を別途用意する（記号は実装時に決定）
- 穴の不変IDは保存時に自動付与し、ユーザーの入力には現れない

### 6.4 復習デッドライン（暫定）

ミス回数のリセット（F-11）を判定する期限。

```
デッドライン = 次回復習日 + max(GRACE_MIN, 直前の復習間隔 × GRACE_RATIO)
ただし GRACE_MAX を上限とする
```

| 設定名 | 初期値 | 根拠 |
|---|---|---|
| GRACE_MIN | 7日 | 短期カードは比例だと猶予が半日以下になる。数日の遅れでリセットが飛ぶのは、遅延を許容するF-04の方針と矛盾する |
| GRACE_RATIO | 0.5 | 固定日数だと長期カードだけ不当に厳しくなるため、間隔に比例させる |
| GRACE_MAX | 60日 | 上限がないと長期カードの猶予が無限に伸び、「放置」を検知できなくなる |

**判定方式**：定期バッチは持たず、カードを回答した時点で「回答日時 > デッドライン」を評価する遅延判定とする。v1でスケジューラを実装せずに済む。

**適用単位**：スケジューリングがカード単位であるため、リセットもカード単位で全ての穴に一括適用する。

**実装上の要求**：3つの設定値はハードコードせず、外部から変更可能にする。BlankLogを全件保持しているため、値を変更した際は過去分を再計算できる。

> この数値は机上で正解を出せる性質のものではないため、あくまで初期値と位置づける。1か月の実運用データ（リセット発生率、猶予日数の分布）をもとに再検討する。

## 付録A：意思決定記録（ADR）

### ADR-001：表裏を二重管理しない

- **状況**：表（伏せ字あり）と裏（正解）の両方を保存するか
- **決定**：裏のテキストのみを保存し、表は記法の置換により生成する
- **理由**：二重管理は編集時の不整合を生む。生成コストは無視できる
- **影響**：記法パーサが単一障害点になるため、テストを厚くする

### ADR-002：穴は位置ではなく不変IDで管理する

- **状況**：穴ごとのミス回数を、カード編集をまたいで保持する必要がある
- **決定**：穴の生成時に不変IDを付与し、統計はIDに紐づける
- **理由**：板書カードは後から加筆されることが前提のため、位置で識別すると加筆のたびに以降の統計が全てずれる
- **影響**：保存時にIDを自動付与する処理が必要になる。ユーザーの入力記法は `〈 〉` のまま変わらない

### ADR-003：文字数制限は維持するが、引用は例外扱いとする

- **状況**：文字数制限が引用によって圧迫される（課題D）
- **決定**：本文の文字数制限は維持する。引用・出典は将来的に別枠へ分離する（v2）
- **理由**：文字数制限は要約を強制するため学習上は有益であり、撤廃すべきではない。一方、参考書の定義文などの引用はそもそも要約の対象ではなく、制限の設計意図の外にある
- **影響**：v1では引用も本文枠を使う。v2で別枠を追加する際、既存カードの移行方法を検討する必要がある

### ADR-004：ミス回数のリセットは記録の削除ではなく集計起点の移動で行う

- **状況**：復習デッドラインを超過した穴のミス回数をリセットしたいが、統計データは失いたくない
- **決定**：BlankLog は全件保持したまま、Blank の `resetAt` を更新する。現在ミス回数は `resetAt` 以降の誤答件数として都度導出する
- **理由**：カウンタを直接減算すると過去の記録が復元不能になる。起点の移動であれば、後から集計条件を変えて再分析できる
- **影響**：ミス回数は保存値ではなく導出値になるため、表示のたびに集計が走る。カード数が増えた際の性能は計測対象とする

### ADR-005：復習間隔の巻き戻し基準は「1つでもミス」とする（暫定）

- **状況**：1枚のカードに20箇所以上の穴がある場合、どこまでのミスを許容して間隔を伸ばすか
- **決定**：v1では、1つでもミスがあれば again として扱う
- **理由**：判定が単純で実装コストが低く、記憶の定着という目的に対して安全側に倒れる
- **懸念**：穴が多いカードほど間隔が伸びなくなり、実質的に毎回出題され続ける可能性がある
- **再検討**：v1運用開始から1か月後、「間隔が一定以上伸びていないカードの割合」を計測し、緩和の要否を判断する（Q-06）

### ADR-006：フロントエンドとバックエンドを分離しない

- **状況**：画面とAPIを別プロセスとして構成するか、1つに統合するか
- **決定**：Next.jsで統合する
- **分離した場合の利点**：
  - 負荷の偏りに応じて片方だけスケールできる
  - 片方だけをデプロイでき、障害の影響範囲も分かれる
  - フロントとバックで異なる技術を選べる
  - 複数クライアント（将来のネイティブアプリ等）でAPIを共有できる
  - 障害発生時の切り分けが容易
- **不採用の理由**：上記の利点はいずれも「規模が大きい」「チームが複数」「クライアントが複数」のいずれかを前提とする。本プロダクトは想定同時利用者3名・開発者1名・Webクライアントのみであり、どの前提も満たさない。一方で管理対象（起動プロセス、CORS設定、Dockerコンテナ、デプロイ先）は確実に2倍になる
- **影響**：段階5のCDにおいてデプロイ対象が1つで済む。ただし将来の分離可能性を残すため、ADR-007の方針を併せて採用する

### ADR-007：ロジックをフレームワーク非依存の層に隔離する

- **状況**：Next.jsのAPI実装（`route.ts`）にロジックを直接書くと、将来の分離時に全面的な書き直しが必要になる
- **決定**：SM-2の計算やDB操作は `lib/` 配下のNext.js非依存モジュールに置き、`route.ts` はそれを呼び出す薄い層に留める
- **理由**：
  - 分離が必要になった際、移植対象を `route.ts` の薄い層のみに限定できる
  - ロジックがフレームワークに依存しないため、サーバーを起動せずに単体テストできる（段階4のCIが容易になる）
- **影響**：ファイル構成の規律が必要になる。実装初期からこの分割を守る

### ADR-008：Goを採用しない

- **状況**：Platform Engineering志望としてGoは有力な選択肢である
- **決定**：v1ではTypeScriptに統一し、Goは採用しない
- **理由**：新言語の習得と初のWebアプリ完走を同時に行うのは、2時間／日・10月末という制約下では完走リスクが高い。Goは本プロジェクト完了後にも学習できるが、締切は動かせない
- **再検討**：v1完成後、または段階6以降のツール実装時に検討する
